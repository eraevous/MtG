# Grammar layer: data dictionary

This file defines every column in the review CSVs, every categorical code, the naming convention for concepts and
hooks, and every concept. It is generated by `dictionary.py`. Sections 1–6 are hand-written in
`dictionary_head.md`. Section 7 is built from the database, so it always matches the current build.

## 1. How the names work

Two kinds of names appear in the `semantics` column. They come from different places.

**Hooks**, such as `card.draw`, `spell.cast`, `attacker.declared` and `combat.damage`, are DIO v3.1.1's own
vocabulary (§4.2). Nothing here invents them. The grammar layer has to emit DIO's names, because DIO is the
governing schema. A hook is written `<subject>.<what happened>`:

- The first word names **what the event is about**. That is the family of game thing the rules talk about, not an
  object in the programming sense. There is no "attacker object" or "combat object".
- `attacker.declared` reads "a creature was declared as an attacker" (CR 508.1). It is the event that "whenever …
  attacks" listens for. "Attacker" is the rules' word for that role.
- `combat.damage` reads "combat damage was dealt" (CR 510). "Combat" here means "of the combat damage step". It
  is what separates it from `noncombat.damage`.
- `permission.cast`, `turn.step.begin` and `mana.add` work the same way: the domain first, then the occurrence.

Where the first word is a real game object (`permanent.dies`, `spell.cast`, `token.create`), that is because the
rules phrase the event about that object.

**Concept ids**, such as `op.card.draw` and `ev.spell.cast`, are this layer's own names. Each one is a prefix
plus the hook it points at. The prefix says what kind of meaning it is (section 7 lists them all). The prefix is
needed because one hook can stand behind three different meanings:

| Card text | Concept | Kind |
|---|---|---|
| "whenever a creature becomes tapped" | `ev.permanent.tap` | event: it happened, so a trigger can fire |
| "tap target creature" | `op.permanent.tap` | operation: the ability does it |
| "as long as it's tapped" | `st.object_status` | state: it is true right now |

An operation records what it *intends*, never the confirmed event. `op.permanent.destroy` intends
`permanent.destroy`. Whether a `permanent.dies` event actually follows is a rules question: regeneration,
indestructible and replacements can all intervene.

**Fair criticism.** Dotted names do look object-oriented. If plain-language labels would read better while you
review, the CSV can carry a "reads as" column built from each concept's label (section 7). The ids themselves
should stay as they are, because they are DIO's.

## 2. Review CSV columns (`review/template_review_*.csv`)

| Column | Meaning |
|---|---|
| `frame_id` | Row id of the template in this build. **It can change between builds.** Verdicts are keyed to the shas, not to this id. |
| `role` | The grammatical role of this piece of an ability (section 3) |
| `template` | The text with the specifics replaced by typed slots (section 4). One template covers every card that phrases it the same way. |
| `completeness` | How much of the template the rules account for (section 5) |
| `mechanical_class` | A rough topic bucket, used only to spread the review sample across kinds of mechanics (section 6). It has no rules meaning. |
| `flags` | Warnings for this row (section 6) |
| `corpus_cards` | Number of cards in all of Scryfall that use this template |
| `collection_cards` | Number of cards you own that use this template |
| `semantics` | What the template means, as one line (section 2.1). **This is the thing you approve.** |
| `concepts` | The concept ids that the semantics are built from |
| `dio_status` | The DIO status of each concept, in the same order (section 6) |
| `examples` | Up to three cards using the template, owned cards first, with the exact text |
| `semantics_sha` | Fingerprint of the semantics. If a later build changes the meaning, your verdict goes stale instead of carrying over. |
| `verdict` | **You fill this in:** `approve`, `reject` or `fix`. Leave it blank if you haven't reviewed the row. |
| `corrected_concepts` | **With `fix`:** the full correct concept set, space separated, each written `concept_id[:RELATION]` |
| `note` | **Free text for you** |

### 2.1 Reading the `semantics` line

The parts of a template are separated by ` ; `. Each part is one of these units:

| Unit | Form | Meaning |
|---|---|---|
| `TRIGGER any of [...]` | `TRIGGER any of [battlefield.enter(subject=#0) \| attacker.declared(subject=#0)]` | One trigger condition. Any one of the alternatives satisfies it (DIO §5.1). |
| `REPLACEMENT[mode]` | `REPLACEMENT[substitute] permanent.dies -> exile.enter(...)` | A replacement effect: the proposed event is rewritten into the resulting one (DIO §5.4). The modes are `substitute` (X instead of Y), `modify` (Y, but changed) and `prevent`. |
| `RESULT <relation> <concept>[hook](args)` | `RESULT PRODUCES op.card.draw[card.draw](object=#0)` | What the ability does |
| `COST CONSUMES ...` | | What is paid |
| `CONDITION OBSERVES ...` | | A state or history the ability checks |
| `AMPLIFIER MODIFIES ...` | | "for each …" or "equal to …" |
| `TIMING`, `RESTRICTION`, `CAPACITY` | | When something may happen, how long it lasts, limits |
| `PROCESS STRUCTURE proc.*` | | How parts link: "if you do", "then", "when you do" |
| `CHOICE STRUCTURE choice.*` | | Modes and choices |
| `KEYWORD EXPANDS_TO kw.*` | | A keyword. It expands to its rules definition. |

`#0`, `#1` and so on refer to the template's slots in order. `#0` is the first `<...>` in the template. For
example, `return <obj.target> from <zone> to <zone>` → `(object=#0, from=#1, to=#2)` says which slot fills which
role. A wrong role assignment, such as source and recipient swapped, is a reason to `reject` or `fix`.

**Relations** say what a result does to the game:

| Relation | Meaning |
|---|---|
| `PRODUCES` | Makes a new occurrence or thing: draw, create a token, put a counter, deal damage |
| `CONSUMES` | Uses something up: pay life, sacrifice, spend mana |
| `TRANSFORMS` | Moves or changes an existing thing: exile, return, gain control |
| `MODIFIES` | Changes characteristics or numbers: +1/+1, gains flying, costs less |
| `PERMITS` | Allows something: "you may cast …", "you may play …" |
| `PREVENTS` | Stops something: counter a spell, "can't block", "enters tapped" |
| `OBSERVES` | Reads the game without changing it: triggers, conditions |
| `EXPANDS_TO` | A keyword's macro |
| `STRUCTURE` | Links between parts. These have no game effect of their own. |

## 3. `role`: the parts of an ability

| Role | Meaning | Example |
|---|---|---|
| `trigger_event` | What a triggered ability waits for | "Whenever a creature dies" |
| `condition` | An "if" or "as long as" | "if you control an artifact" |
| `cost` | Something paid before the colon, or as an additional cost | "{T}, Sacrifice a creature" |
| `cost_header` | "As an additional cost to cast this spell" | |
| `effect` | One instruction that is carried out | "draw a card" |
| `static` | An ability that is just true while the card is on the battlefield | "Creatures you control get +1/+1" |
| `amplifier` | A scaling phrase | "for each artifact you control" |
| `duration` | How long an effect lasts | "until end of turn" |
| `timing` | When it may be done | "Activate only as a sorcery" |
| `restriction` | A limit on it | "Activate only once each turn" |
| `link` | A connector between instructions | "If you do", "then", "When you do" |
| `replacement`, `replacement_marker` | "If … would …, instead …" | |
| `delayed_trigger` | A trigger created by an effect | "At the beginning of the next end step, …" |
| `mode_header` | "Choose one —" | |
| `keyword` | A keyword line | "Flying", "Ward {2}", "Station" |
| `structure`, `residue` | Layout lines (level-up, chapters) and text left over after splitting | |

**Ability kinds**, as used in the contracts and the reports: `keyword`, `triggered`, `activated`, `spell` (what
an instant or sorcery does), `static`, `replacement`, `mode`, `loyalty`, `chapter`, `additional_cost`.

## 4. Slots in templates

| Slot | Stands for | Example of what fills it |
|---|---|---|
| `<self>` | This card | "this creature", "~" |
| `<obj.q>` | A described object, quantity first | "a creature", "two cards" |
| `<obj.target>` | A targeted object | "target creature an opponent controls" |
| `<obj.each>`, `<obj.all>` | Every object of a kind | "each creature", "all tokens" |
| `<obj.another>` | Another object (excludes this one) | "another creature you control" |
| `<obj.upto>` | "Up to N" | "up to two target creatures" |
| `<obj.ref>`, `<ref>` | A back-reference | "it", "that creature", "those cards" |
| `<obj.bare>` | An object with no quantity | "creature" in "Choose a creature type" |
| `<obj.attached>` | What it's attached to | "enchanted creature", "equipped creature" |
| `<player.you>`, `<player.you_poss>` | You, your | |
| `<player.each>`, `<player.target>`, `<player.ref>`, `<player.q>` | Each player or opponent, a target player, "that player", "an opponent" | |
| `<zone>` | A zone | "your graveyard", "the battlefield" |
| `<mana>` | Mana symbols | "{W}{B}", "{2}" |
| `<n>` | A number | "2", "X" |
| `<pt>` | A power/toughness change | "+1/+1" |
| `<counter>` | A counter kind | "+1/+1 counters", "charge counters" |
| `<kw>` | A keyword inside text | "gains flying" |
| `<color>`, `<energy>`, `<tap_symbol>` | A colour, {E}, {T} | |
| `<granted_ability>` | A quoted ability that is granted | Its text becomes its own ability, with its own rows |

The values that fill the slots are not in the template. They are stored per card, and the contract turns them
into DIO qualifiers: type, controller, "another", token, cardinality, zone, and so on. That is why one template
can cover "a creature" and "an artifact you control" alike, and why approving a template doesn't approve every
card's specifics.

## 5. `completeness`

| Value | Meaning | What approving does |
|---|---|---|
| `complete` | Every word of the template is accounted for by a rule | Counts toward the headline metric once approved |
| `partial` | Some meaning was found, but words are left over | Records your judgement, but never counts as reviewed, because the leftover words may matter |
| `none` | No rule matched | Needs a `fix` row or a new rule |

## 6. `flags`, `dio_status` and `mechanical_class`

**`flags`** (they can be combined, separated by spaces):

| Flag | Meaning |
|---|---|
| `addendum_dependent` | Uses a concept whose DIO definition is waiting on the A1–A7 addendum. Approve it only if you're confident of the meaning whatever A1–A7 decides. |
| `unmapped` | No concept at all |
| `partial` | Same as completeness `partial` |

**`dio_status`** (one per concept):

| Value | Meaning |
|---|---|
| `ontology_defined` | DIO v3.1.1 defines it directly |
| `addendum_pending` | Depends on A1–A7: keyword macros, `tapped_for_mana`, step/phase begin, goad, and similar. Belongs to the SQLite thread. |
| `language_layer` | A label used only here, for things DIO v3.1.1 has no identifier for yet: extra turns, win/lose the game, hand size, "must attack", exchange, random outcomes, "if able", level bands. It is not a proposed new DIO primitive. |

**`mechanical_class`**: the first matching bucket, in this order:

1. `replacement`
2. `modal`
3. `mana`
4. `sacrifice`
5. `land_search` (any library search)
6. `death_trigger`
7. `enter_trigger`
8. `combat_trigger`
9. `cast_trigger`
10. `step_trigger`
11. `tokens`
12. `counters`
13. `removal` (destroy, exile, damage, counter a spell)
14. `card_flow` (draw, discard, mill, return)
15. `life`
16. `pump_grant`
17. `keyword`
18. `cost`
19. `condition`
20. `other`
21. `unmapped`

It exists so the 74-row sample covers every kind of mechanic about equally. Ignore it when judging meaning.

**Certainty**, as used in contracts and discovery:

| Value | Meaning |
|---|---|
| `guaranteed` | Always happens |
| `optional` | "You may" |
| `conditional` | Behind an "if" |
| `possible` | Discovery only: part of the text is unread, so the link can't be ruled in or out |
