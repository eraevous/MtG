# 2026-11-01 mtgtools 0.3.1: fixes from the first practical-question run

**Trigger.** Zach asked to get back to using the tools on everyday questions. A run of eight practical questions on r20261031 (ownership, function gaps, swaps, a sacrifice package, an interaction check, typal census, claim checking) found four wrong answers in `explore`/`hypothesis`.

**What changed (tool).**
- Cost payment events (sacrifice, discard) recorded under `initiation` now feed links. Viscera Seer → Blood Artist had no link at all; it is now `compatible` (`basis: paid_object`). The paid object's type decides compatibility; an artifact sacrifice stays unresolved against a creature filter because artifact creatures exist.
- A trigger with "this creature or another creature" alternatives is not treated as self-only (Blood Artist, Zulaport-style triggers).
- A trigger that names its own card ("Sharuum enters") is self-only. This reads the trigger phrase, like the existing "this"/"~" check (C-010 applies: it should move upstream, C-023).
- A target player never "acts on" a card (Blood Artist was listed as acting on Viscera Seer).
- A loop through a finality-counter return or through an instant/sorcery is listed as `once_only` under `loops_contested`, not as a loop (Cirith Ungol Patrol + Wolfbat).

**Trade-off.** Seeing cost events multiplies links on sacrifice themes (140 → ~1,100 for free black cards) and moves ~100 grammar-layer loops from contested to listed. Most of those loops are `possible`-certainty noise from the grammar layer (e.g. a Clue maker "enabling" a sacrifice-a-creature cost). They were contested before for the wrong reason; now their certainty label carries the weight.

**Data vs tool.** Two of the four fixes are read-time workarounds for projection gaps (C-023). The loop list's quality is a grammar-layer data issue. Per Zach's standing rule: the larger lever is the data layer (cost events in feeds, token characteristics, role-detector conditionals such as Amalia's "if its power is exactly 20" counted as a wipe).
