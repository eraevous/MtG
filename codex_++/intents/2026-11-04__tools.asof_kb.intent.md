# 2026-11-04 As-of collection databases for historical replay

**Trigger.** Kate's preflight for the blind two-arm historical test (2026-11-04): mtgtools must answer each historical question from the collection as it was on that date. If it can see the late-October KB collection, the full-tools vs lookup-only comparison is invalid.

**What.** `tools/asof_kb.py` copies a KB release and replaces ownership with a dated inventory fixture. It recomputes owned/assigned/free, replaces the deck lists, removes cards not owned on that date from every card-keyed table, and drops inventory role tags, which came from a later inventory. It also writes a manifest naming the fixture, and a dated policy (or `not_recorded`). mtgtools reads a `collection_policy.json` beside the database before falling back to `decks/collection_policy.json`. Grounding and `find` freshness report the as-of date. `compare` refuses the later `data/` workbook against an as-of database. Both test arms get the same database, so their raw facts match.

**Trade-offs.**
- Card meaning (Oracle text, contracts, reviews) stays at the base release. Arm A tests today's tools on yesterday's collection, as Kate's protocol asks. It is not a reconstruction of the tools as they were then.
- Only the derived copy is modified, and the release KB is untouched. That copy is rebuilt from fixture + release, so this is not a hand edit. The copy drops the release's append-only triggers, and the manifest says so.
- A fixture name the KB lacks (a card owned then but not in the 2026-10-24 inventory) cannot be added without Oracle data. It is listed under `gaps.fixture_names_not_in_kb`, not invented.
- Rows whose status reads planned, proposed or similar are `planned_only` and hold no copies (Shanid, S17/S26).
